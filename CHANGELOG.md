# Changelog

## Unreleased
- **A read that gets no answer is asked again, and a wait no longer ends on one timeout; the sync wait says what the firewall said; a plan built on older settings cannot be approved.** Seen live in a production pilot: five firewalls failed on `The read operation timed out` after a successful install and reboot (once while waiting out the boot-time jobs, once at verification), although other firewalls answered through the same Panorama at the same moment. Each read-only query is now tried up to 3 times (a poll interval apart) before it counts, the waits (`reboot`, `suspend`, `sync`, job polling) treat a look that failed as "not yet" and end only at their own time limit (the message then says the last look failed, so it is not mistaken for a "no"), and a config sync that never reads synchronized reports what the last look showed ("read False each time", or "the firewall's HA reply could not be read"). Also fixed: in the shell, a plan that was read, then followed by a change to the settings (Alt-S), could still be approved within its 30 minutes with the old settings (for example a `sync_to_peer` step the new settings had switched off); approval is now refused, naming what changed, until the plan is read again.
- **An unrecognized flag in the settings file is ignored with a warning, not a refusal.** A name in the file that is not a setting (a typo, a hand edit, a flag removed in a later version) is skipped, the rest of the file applies, and each command says once "unrecognized flag 'x' in the settings file is being ignored". The settings form names it in its opening message, and saving (which rewrites the file with only the known settings that differ from the defaults) removes it. Still refused: a secret-looking name, a flag that changed meaning (`failover_band`, `post_upgrade_band`, with a message naming the replacements) and any unknown name typed with `--set`, so a typo on the command line is caught. Removing a setting from the tool no longer breaks a saved settings file.
- **`job_stall_s` now defaults to 300 s (was 180).** Seen live: a software download reaches 99% quickly, then the firewall's software manager loads the image without moving the percentage, and that last step can take longer than the whole download. Three minutes gave up on healthy downloads; five is the new default. Raise it further on a slow site, or set 0 to rely on `download_timeout_s` alone.
- **A download that stops moving is given up on (`job_stall_s`, default 180 s), and the per-firewall list always shows an HA pair as one entry.** While waiting for an image or content download, if neither the job's status nor its percentage has changed for `job_stall_s` seconds, the task fails with "made no progress for 180s (stuck at ACT 19%) ... look with `show jobs id N`" and `prepare` moves on; at half the limit the log says "no progress for 90s, given up on at 180s". A job the firewall reports as queued is waiting, not stalled; installs and commits are not judged this way (they keep their own timeouts); the job is not cancelled on the firewall; 0 turns it off. In Settings under Images, disk and time, and part of the plan hash. Unit-tested against the job reply shape seen on a lab firewall (status ACT, result PEND, progress 19); **not run against a real stalled download.** Separately, the `prepare` screen's list now always shows both members of an HA pair on one row (before: only when the pair had content or config work, so a pair with only a download showed as two rows, or one when the other member had nothing), listing a member that has no work of its own too. The plan records the pairing (`pairs`, view only, not in the hash).
- **`prepare` counts every firewall it worked on, and the download and install waits default to 30 minutes.** Fixed: a passive member that the pair's own steps update (content, backup, config sync) but that has no task of its own (its image was already there) was worked on and journaled but left out of the outcome, so the report said "17 of 20 firewalls" for a fleet of 24 in pairs. Every step done to a member is now noted under that member as well as under its pair's active member, so both show in the outcome, the report and the totals (the failure count is unchanged). Also: `download_timeout_s` and `install_timeout_s` default to 1800 s (were 3600); a stuck job fails the task after half an hour.
- **The shell shows what a note says.** Fixed: the run screens listed a long job's progress lines as "job progress  note" with the message left out, and the header read "running: FW: job progress". A note's message now follows it in the list, and while a job is reporting progress the header shows it ("FW03: content download: job 7 ACT 40% (running for 310s of at most 3600s)").
- **Ctrl-C in the shell always asks first, and quitting stops the rest of a run.** Ctrl-C (or Quit) now shows "Quit panupgrade? Press Ctrl-C again or Y to quit, any other key to stay"; while a real run is changing firewalls the question names it and says the steps in progress will finish first. Before: it only asked while a run was going. Fixed: quitting left the run's queued units to start by themselves once the window was gone (the process lingered on a blank screen while every remaining firewall was worked on, since nothing set the run's stop switch); quitting now sets it for every run started in the shell, so the steps in flight finish and nothing new starts, and the next launch offers to continue the unfinished run (CONTINUE / NEW, or `--resume`).
- **A long content download or install reports its progress, and a failed one ends that pair's work.** While `prepare` waits for a content, antivirus or WildFire job, each poll (every `poll_interval_s`) reads `show jobs id N` and the journal and log get a line whenever the status or percentage changes ("content download: job 7 ACT 40% (running for 310s of at most 3600s)"). A job that finishes with a result other than OK already failed the task at once; new: the rest of that pair's content work (the other member) is skipped, so prepare moves to the next unit instead of spending more time on a pair that cannot be levelled. The wait is not endless: `download_timeout_s` and `install_timeout_s` (3600 s each by default) end it with an error. Unit-tested; not run on a real firewall.
- **Every firewall's label row names its HA role: `Hostname (Model Serial role) Current -> Target`.** The role (active, passive, suspended, standalone) now sits in parentheses after the serial in the plan on screen, the plan text report, the approval list and the shell's upgrade screen; the model stays on the row, inside the same parentheses.
- **The baseline line in the log warns for any count below the noise floor.** The run now writes the floor and `below_floor` into the session baseline record, so the log shows "session baseline 12, below the noise floor of 100 (from A1): the session checks will be skipped" as a warning at the start of the firewall's run, not only for 0. A journal written before this (count only) still reads: 0 or unreadable warns, anything else is information.
- **New setting `session_noise_floor` (default 100): a session count too small to judge is skipped, not judged.** A before/after comparison of 12 sessions of management traffic moves by more than a band for no reason. Below the floor the plan's `session_baseline` check warns and asks for the `no_session_baseline` acknowledgement (naming the floor), `prepare` notes the firewall, and the run skips the fail-over check, the end-of-pair check and a group member's recovery check, each with a warning line. 0 sessions is always below the floor (setting 0 behaves as 1); set 1 to judge anything with traffic. For a group member the floor applies to its own count and to the other members' average separately. In Settings under HA behaviour, and part of the plan hash.
- **A firewall with no sessions (pre-production) is said so in the plan, in `prepare` and in the run, and nothing divides by zero.** Already true: the plan's `session_baseline` check warns on 0 sessions and asks for the `no_session_baseline` acknowledgement, and the run skips the comparisons instead of dividing (every comparison needs a reference above 0). New: the plan's wording now names what is skipped (the check after the fail-over, the check when the pair is done, a group member's recovery check); `prepare` adds a note for each firewall it will upgrade that has 0 sessions, or none readable, now (not for a passive member, which carries none of its own), saying the checks will be skipped; and in the run every skipped check carries a warning (a zero baseline shows as a warning line, not information), so the upgrade report shows exactly where the tool could not look. A group member that had 0 sessions while its neighbours carry traffic is judged against their average, so one that never takes traffic back fails. Not built: a floor below which a count is too small to judge (12 sessions of management traffic is not 0 but a 35% band is 4 sessions).
- **HA pairs get a warn band and a fail band too, and the table is waited for (replaces `failover_band` and `post_upgrade_band`).** New settings `pair_session_warn_band` (0.35), `pair_session_fail_band` (0.80) and `pair_session_wait_s` (60); the two old names are retired and a settings file that still has them is refused with a message naming the new ones. Only the active member sees sessions built on it (the passive holds a copy over HA2), so the count the active member had before the suspend is what the member that takes over must show. **After a fail-over** the new active node is read every `poll_interval_s` until it is no more than 35% short of that count, or the wait runs out (before: one read straight after the suspend, before any settle). Still short: less than 80% short is a warning (the step passes, the log and journal carry it); 80% or more short is a failure: the suspended member is put back into service (`functional`) and the firewall fails, and the message says what the pair is left running ("two versions: A runs x, B runs y" in the default passive-first order, where the passive member is already upgraded). **When the last member is done**, and for the active node's own `verify HA`, the same wait and bands judge the active node against the pair's baseline (before, nothing waited after `go live`); a failure there cannot be undone and is reported. Shortfall only. Unit-tested against the simulator (warn, collapse, wait with a fake clock, active-first collapse leaves both on the old version, last member); **not run on a real pair.** Behavioural change to know about: the old fail-over limit was +/-30% (reverted at 40% short); the failure threshold is now 80% short, and 35-80% short only warns.
- **A stand-alone group member is not finished until its session table is back, and the next member waits for it.** New last step `check service` for every group member (after the undrain): the member's count is compared with its own count from just before it was drained (`group_baseline`, taken when it takes its group slot) and with the average of the other group members now, whichever it is closer to, and the tool waits, reading again every `poll_interval_s` up to `group_session_wait_s` (default 600), until the member is no more than `group_session_warn_band` (0.35) short. The member keeps its group slot through the check, so the next member is not drained until this one is back. If the wait runs out still short: less than `group_session_fail_band` (0.80) short is a WARNING (the step passes, the journal and log carry `warning`, the run goes on); that short or more is a FAILURE (the group is closed like any other failed member). Only a shortfall counts. All three are settings (Settings, Stand-alone groups) and part of the plan hash; the plan shows the step. A simulation judges on one reading. Unit-tested against the simulator with a fake clock, and the slot-holding test fails if the slot is released early; **not run on the real Foxtrot group yet.** Pairs are unchanged: their fail-over and end-of-pair checks still read once (polling for them is not built).
- **A headline verdict at the top of every record.** The plan (text, terminal, HTML) now opens with one line and a facts row. Plan: `READY`, `READY WITH CAUTIONS` (acknowledgements needed, or some firewalls BLOCKED while others can go), `BLOCKED` (none can start) or `NOTHING TO UPGRADE`; facts are target, Panorama, in scope N of M in the fleet (units), traffic-affecting step counts, plan hash. Preparation report: `PREPARED`, `PREPARED WITH WARNINGS`, `NEEDS ATTENTION`. Upgrade report: `COMPLETED`, `COMPLETED WITH PROBLEMS`, `STOPPED`. Coloured green/gold/red in the terminal and HTML. It states what is in the record and what needs attention; it never predicts duration or outcome, and there are no sign-off lines. Not built: naming the previous record's file (the plan hash ties the three together). Unit-tested; the Excel files do not carry it yet.
- **New setting `upgrade_first` (pairs only): `passive` (default, as before) or `active`.** With `active` the active member of an active/passive pair is suspended and upgraded first: its passive peer, still on the old version, takes the traffic, and the session count must stay within `failover_band` (that is how the tool tells the passive member's cabling and session table are healthy), otherwise the member is put back and nothing is installed. The suspended member is then upgraded and released, the other member waits for it, is suspended in turn so the upgraded member takes the traffic back (same check), and is upgraded. Two HA fail-overs per pair instead of one; the original active member is active again at the end, so `restore_roles` has nothing to do. The plan shows it: pair order, the steps of each member, the fail-over count, a fleet caution `upgrade_first_active` to acknowledge, and a `position` (first/second) on each member (so it is in the plan hash). Stand-alone firewalls, load-balanced group members, and a pair with a member missing from the run, or suspended, are not affected. **Also new, for both orders:** when the last member of a pair is done, the active node's session count is checked against the pair's baseline within `post_upgrade_band` and the member fails if the service has not come back (before, only a member that happened to be active was checked, which in the default order is never the case unless `restore_roles` is `restore`). Unit-tested against the simulator; **not run on a real pair.** A matching post-upgrade session check for stand-alone groups is not built yet.
- **The plan puts the problems first and the routine last: red for blocked, and "Not planned" is grouped by reason.** In the text, terminal and HTML plan, a blocked firewall's line is now red all the way along (a bold word inside the line used to end the red early, so only the tag showed), the Blocked heading is red and Need-your-acknowledgement is gold; in the HTML a blocked row has a red edge and its failing findings are red. Firewalls that are not planned are no longer a block of detail each: one heading per reason (Not in the selection; Stand-alone firewalls left out, with the setting named; Nothing to upgrade; Could not be assessed) and one line per firewall. Only the last three say why, because someone expected those to be in the run. The Excel plan keeps every firewall and every check.
- **Fixed: a stand-alone group member gave up its slot after its FIRST verify.** With no drain profile set (no `undrain` step) the group slot was released at the first `verify`, so a member on a multi-hop path, or one doing an activation reboot followed by an install, let the next member start while it still had installs and reboots to go. It now keeps the slot until its last verify (or its undrain). Not covered by a test that runs the executor; the logic is one condition in `executor.py`.
- **The plan now handles an installed-but-unbooted image instead of only refusing it.** Three cases, all needing an acknowledgement: (1) the pending image **is the target**: the plan is `backup`, `reboot to activate <version>`, `verify` (no download or install; a low-disk reading does not hold it, nothing is downloaded); (2) the pending image is **what the HA peer, or every other member of the firewall's stand-alone group, already runs**: the plan reboots into it first so they are on one version, then goes on to the target from there (the path starts at the pending version); (3) **anything else** stays blocked, with "run a clean-up batch first" and what it is waiting for. A firewall that would also need an Allow Asymmetric Return window is blocked in cases 1 and 2, because that window commits on the firewall and it refuses commits until rebooted. The executor's preflight accepts the pending image only when it is the one the plan named; verification after the activation expects that version; a group member holds its slot (and is drained) across the activation reboot. Unit-tested and checked read-only against f1 (2026-11-17); **the activation reboot itself has not been run live.**
- **Stand-alone outage is a setting, not a button on the upgrade screen.** The review screen had a switch labelled "Standalone firewalls: left out" that looked like a start button and, when nothing was ready, was the only button on the screen. It is gone: `accept_standalone_outage` is now a setting (Settings, Stand-alone groups; `--accept-standalone-outage` still works), and the plan's summary line states which way it is set ("LEFT OUT" or "PLANNED, each is OFFLINE while it reboots"). When nothing is ready the screen says "STARTING IS BLOCKED by the issues listed below" and the button where Approve would be reads "STARTING BLOCKED by the issues below - fix them, then read the plan again".
- **The fleet report is now a written record too, and it flags an installed image waiting for a reboot.** `report` wrote nothing but an optional JSON file. It now also writes `PanUpgrade_FleetReport_<time>` as HTML, text and Excel (Needs attention and Every firewall sheets, with columns for uncommitted config and reboot pending) into the profile's `prepared` folder, `--report-dir` to choose, a warning rather than a failure if it cannot write. "Needs attention" gained the `pending_reboot` case (an image installed and not booted, from `debug swm status`; the running version is named), which the plan already failed on but the report never showed. It also flags low disk space: a firewall with fewer MB free than `min_free_disk_mb` (the plain floor; the plan's own check also considers what has to be downloaded). Verified read-only on f1/f2 (2026-11-17).
- **New check `pending_reboot`: an installed image that was never booted holds the firewall.** A firewall that has had a PAN-OS image installed and not rebooted refuses every commit ("Software has been downgraded, please reboot the device before committing the configuration"), so a run that starts on it fails half way. The check reads `debug swm status` (the software manager's partition table: the running partition is `RUNNING-ACTIVE`, an installed image waiting to be booted is `PENDING-CHANGE`) and fails with the version and "reboot it first"; the executor's own preflight refuses it too. The job table is deliberately not used: it rotates and old install jobs disappear. **The read-only command filter gained exactly one debug command**, `debug swm status`, matched whole (nothing else starting with `debug` passes, and extra words are refused). It changes nothing on the firewall. Not required: a firewall whose account may not run it, or that prints a table the parser does not understand, shows "no data" for this check instead of being blocked. Verified read-only on two lab firewalls (2026-11-16); the table's other states are unseen.
- **A commit the firewall refuses now says why, and leaves nothing behind.** A firewall that had been downgraded and not yet rebooted answers any commit with "Software has been downgraded, please reboot the device before committing the configuration". The asymmetry window read that reply as a commit with no job and reported only "no job id in the reply", then tried to "restore" by committing again (refused again), so it raised an ALERT that the firewall was still set to accept asymmetric traffic when nothing had ever been committed and only the candidate configuration held the edits. Now the refusal text is shown with "Reboot it first, then run again", the candidate edits are taken back with `revert config` (the window has already checked nothing else was uncommitted), the firewall is not listed as needing a restore, and the journal records the open as failed with `changed: false`. The write allow-list gained exactly one command, `revert config`. Seen on a lab firewall (2026-11-16); the fix is unit-tested, not yet run live.
- **Three records per cycle: Plan, Preparation report, Upgrade report.** `plan` now writes `PanUpgrade_Plan_<target>_<time>` (HTML, text, Excel) into the profile's `prepared` folder (`--report-dir` to choose; `--out` still writes the machine-readable set). `prepare` no longer writes a "proposed plan"; its run log is renamed `PanUpgrade_PreparationReport_...` and `upgrade`'s `PanUpgrade_UpgradeReport_...`, and both now also come as Excel (a Result sheet and an All activity sheet).
- **Verified on the lab firewall: the asymmetry window's reads and writes.** `show session info` names the in-force flag `tcp-nonsyn-rej` (the reader looked for `tcp-reject-non-syn` and refused; fixed). With that, the tool's own set and restore took all three knobs from the factory state to tolerant (flag off, `session/tcp-reject-non-syn` no, `asymmetric-path` bypass) and back to exactly the first reading.
- **Lab findings (test fleet, 2026-11-07) change the load-balancer drain.** On a Panorama-managed firewall an interface management profile that a template pushes, and the interface assignment of it, answered "Object cannot be overridden" to the override action, and "may need to override template object first" to a plain set: neither can be edited locally. A complete same-named local copy, sent with `override` at the profile list, is accepted and takes precedence (merged view shows the change); deleting that local entry returns the template's value. The drain now does exactly that for a template-owned profile (the journal records the profile's origin), and its restore deletes the local copy instead of writing values back; a firewall-local profile is edited and restored value by value as before. Verified by running the tool's own drain and restore on the lab firewall. The persistent TCP settings are not template-owned there: `deviceconfig/setting/session/tcp-reject-non-syn` and `.../tcp/asymmetric-path` were set, committed and deleted on the firewall through Panorama (`target=`), and the running configuration returned to having neither.
- **`probe-config`: read-only look at how a firewall presents the settings the asymmetry window and the drain edit.** Template-owned settings are not in the local XML like local ones, so editing and restoring them node by node cannot be designed by guessing. `panupgrade probe-config --serial S` writes the exact XML (attributes kept) of `deviceconfig/setting/tcp`, `deviceconfig/setting/session`, the interface management profiles and the interfaces that name one, from `show config running / candidate / merged / pushed-template / diff`. Only `show` commands are sent. **Known gap, to be fixed from its output:** the window and the drain restore a value with `set`, which for a template-owned value leaves a permanent local copy instead of removing the override. Design direction chosen by the owner: when `pending_changes` permits upgrading a firewall with candidate changes, save the running config under a name before the window and load it back afterwards if that is simpler than undoing node by node; otherwise restore the recorded XML exactly.
- **Draining a group member from its load balancer, and the asymmetry window now sets all three knobs.** `lb_drain_profile` names the interface management profile a load balancer's probe relies on, `lb_drain_probe_protocol` (`ssh`, `http`, `ssh+http`, ... `ping`) what it probes with, `lb_drain_wait_s` how long to wait. Each group member gets a **drain** step before its reboot (the probe's protocol is taken out of the named profile, committed on the firewall) and an **undrain** step after its last verification; the profile is put back even when the member failed (also by an end-of-run sweep, and for a stopped run), and a profile that cannot be put back is an ALERT with the values it should hold. The asymmetry window now records and sets the persistent `deviceconfig setting session tcp-reject-non-syn` as well, because the operational `set session tcp-reject-non-syn` is dropped by the next commit or reboot: all three are recorded first, "not set" is put back by deleting the node. The write allow-list gained exactly: one protocol (ssh, http, https, ping) set yes/no or removed in one named interface management profile, and the `session tcp-reject-non-syn` node. Unverified on a real firewall (see docs/running.md).
- **Stand-alone groups, and an asymmetry window for pairs and groups.** (1) A firewall list can put firewalls that are not HA pairs in a *group* (`SERIAL, group name` in `upgradeList.txt`; **G** on an Included firewall in Choose firewalls). A grouped firewall is no longer held back as a stand-alone outage; its reboot is planned as lost redundancy, and `group_reboot_tolerance` (default 1) is how many members of a group may be out of service at once (a firewall holds a slot from its reboot to the end of its verification; a member that fails while holding one closes its group, and the rest are not started). (2) `pair_tolerate_asymmetry` (default false) and `group_tolerate_asymmetry` (default true, used only when a group exists): before the first member of a pair or group is touched each member's three knobs (`set session tcp-reject-non-syn`, which PAN-OS drops at the next commit or reboot, and the persistent `deviceconfig setting session tcp-reject-non-syn` and `deviceconfig setting tcp asymmetric-path`; "not set" is a value, put back by deleting the node) are recorded, then set to no, no and bypass (a commit on the firewall; refused when other changes are uncommitted), and put back after the whole pair or group is finished, successful or not. Every change and restore is journaled; a firewall that cannot be restored is an ALERT with the commands to fix it, and makes the run exit 1. The window is in the plan (hash, `asymmetry_window` caution to acknowledge). The settings screen's HA behaviour is now two sub-lists, Active/Passive pairs and Stand-alone groups. The write allow-list gained exactly: `set session tcp-reject-non-syn yes|no`, a config edit of `asymmetric-path` (set bypass|drop, or delete) or of `session tcp-reject-non-syn` (set yes|no, or delete) and a commit. **The live half is unverified**: the reply shape of `show session info`, that Panorama accepts a proxied config edit and commit with `target=`, and that the runtime flag survives the commit; try it on a lab firewall first. Pairs: only planned members are covered; an unplanned peer is not touched.
- **Settings screen: one word for "plan it anyway", and colour that says what a choice means.** `ha_config_unsynced` and `blocked_peer` took `block | caution`; every other setting that loosens a check says `warn` (`pending_changes = block | warn | ignore`), so they now take `block | warn` too. A settings file or `--set` that still says `caution` is read as `warn`. On the Alt-S screen `block` is red and `warn` is gold wherever they are chosen and in the explanation beside the list, and a setting that differs from its default is drawn in blue (the `*` mark stays). The risky-setting lines under the explanation now begin "Warn:" instead of "Caution:", and `panupgrade settings` prints them as `warn:`. Not renamed: a plan's cautions (the items an approval acknowledges, their `ack` codes and the `caution` verdict in saved plans), which are a different thing from a setting's value.
- **Select screen: a "Deselect all" button, and a regex mode for host names.** The buttons are now Save, Save & Exit, Deselect all (empties the Included list; the C key in that table did the same), Quit without saving. The host name filter keeps its two modes, `pattern` (a glob: `*` and `?`, the whole name must match, so `^` and `.` are plain characters there) and `contains`, and gains a third, `regex` (`--name-regex` on the command line): a regular expression found anywhere in the name, `^` and `$` anchor it, `.` is any one character, case ignored. A broken expression is shown in red and ignored on the screen, and refused with the reason on the command line. The glob stays the default because existing lists and habits use it; typing a regular expression into the glob mode was never going to behave.
- **A long message in the by-firewall log is wrapped, not cut off.** The log beside the list of units drew each event on one row and clipped it at the screen edge, so a firewall's own refusal ("install ... FAILED: 0079...: inst") could not be read. Each line is now wrapped to the width of the pane (indented on the next rows) and scrolling counts the wrapped rows. The wrap follows the terminal width, in the two-column layout and the narrow single-column one.
- **Unneeded images are deleted highest release first.** `prepare` with `delete_unneeded_images` deleted in text order, lowest first, so a base image (for example 10.2.0) was asked to go while a later release built on it (10.2.10-h42) was still on the firewall; the firewall refused, and that firewall's `prepare` failed (lab run, 2026-11-04). The plan now lists the images highest first and the run sorts them again before deleting, so an older plan file is handled too. Inferred from that one refusal followed by a successful delete of the later release; the firewall's own refusal text was cut off in the log and has not been read in full.
- **A suspended HA member can be upgraded** (`upgrade_suspended`, default true; Alt-S, HA behaviour). It used to be blocked with "HA state is 'suspended'". A suspended member carries no traffic, so it is planned like a passive member: no fail-over, no session baseline (taken from its peer), and first in its pair. The tool never suspends it again and never re-enables it as a choice of its own: after the reboot it is expected to rejoin as passive, and if it is still suspended that firewall fails with a plain message and its active peer is not started. **Unverified on a real firewall** whether the reboot clears a suspension (the simulator keeps it unless a test says otherwise), so check it on a test pair before relying on it. `upgrade_suspended=false` blocks a suspended member and names the setting. It is part of the plan hash, so changing it voids an earlier approval. Not changed: a firewall with uncommitted candidate config is still blocked by `pending_changes`.
- **The firewall's own auto-commits are waited out before the next step** (`settle_after_failover_s` 60, `settle_after_reboot_s` 120; Alt-S, HA behaviour; 0 turns a window off). The 2026-11-03 system logs of all ten lab firewalls showed that the firewall queues a full auto-commit of its own at moments the tool cannot see coming: 18-24 s after each of four suspends (65-113 s long), and a second one 4-52 s after a rebooted member reconnects to Panorama (63-143 s long, on all five). A "no jobs" look before one starts proves nothing, which is how two installs were refused and one verification failed, and how two pairs were failed over onto a member that was still committing. After the suspend, and after the reboot, the step now waits the window and then until `show jobs all` is empty (up to `busy_wait_s` more), and says in the log when it finds a commit. The look is one query (`show jobs all`) instead of the ten-query state read, so it is also fresher. A simulation does not wait. The cause of the post-suspend commit is not understood: three later lab suspends produced none, so the wait checks for the job instead of assuming it.
- **A busy firewall is waited for, not failed** (`busy_wait_s`, default 900 s; Alt-S, HA behaviour). From the 11.1.16-h4 lab run: two active members were refused the install ("A commit is in progress. Please try again later.") seconds after the fail-over although the jobs list had just shown nothing unfinished, and a firewall that had just rebooted failed the verification for one running job. Now the install, once `show jobs all` is clear, is asked again every `poll_interval_s` while the firewall answers "commit in progress" / "try again later" (each wait is a line in the log; any other refusal fails at once), and the verification waits for the jobs to finish before it reads the version. Past `busy_wait_s` the step fails with the firewall's own words. Config-sync waits keep `sync_timeout_s`.

All reads still share the one `api_rate_per_s` budget, so raise it if the limiter, not the firewalls, is the wait. Progress now reads "Reading firewall k of n" in the order the reads finish.

- **Fixed: every `prepare` overwrote the same report files.** The sign-off report was named `report-<target>-<time>` and the extension was then swapped in with `with_suffix`, which treats the last dot of a target such as `10.2.10-h42` as an extension, so each run wrote `report-10.2.html/.txt/.xlsx` and replaced the last one. Each entry says how many versions it holds and whether it contains the running, a downloaded or the latest one.
- **Skip-version upgrades, and the legacy step-through.** The path rules are now the ones Palo Alto documents (the knowledge-base article on base images, the "Determine the Upgrade Path" pages, the PAN-OS 11.0 Skip Software Version Upgrade feature, and the LIVEcommunity thread): from 10.1 on only the target is installed and up to three feature releases may be skipped; below 10.1 every feature release is stepped through (download its base, install its pinned latest preferred maintenance release), then it skips. The target's base image is downloaded, never installed; the bases of the releases skipped over are NOT downloaded for now (`skip.download_skipped_bases` in the rules turns that on), because the LIVEcommunity example got by without them and the lab run 10.2.10 -> 12.1.10-h2 is to settle it. The base is the **lowest non-hotfix version the firewall itself offers** for that release (x.y.0, unless that build was recalled and replaced), read from its own software list; the rules' `base_image` and x.y.0 are the fallback when that list is not available, and a release the firewall does not list at all is a refusal. A jump beyond three skipped releases stops at a waypoint it installs. The old `direct_from`, `stepping_install` and `min_source` rule keys are gone.

A cross-feature downgrade follows the same skip rule in the other direction (10.1 or later, at most three skipped), carries its own acknowledgement about the older release's configuration, and is marked unverified.

The base of a feature release is `x.y.0` unless the path rules name a replacement (`stepping_install`), for a build that was withdrawn. An image whose name cannot be read is never deleted, and nothing is deleted without a target or without the firewall's own image list. The backend refuses to delete the running image however it is asked, and each deletion is checked afterwards, not assumed. - **Config sync is only asked before the first member of a pair is upgraded.** Members on different PAN-OS versions cannot sync configuration (base code and the built-in application data differ), so once the first member is upgraded there is nothing to decide and nothing to collect. `verify HA` no longer fails a firewall for "HA1 config sync is False" (that stopped a passive that had upgraded perfectly and held its active, in the first real run, for every pair); when both members run the same version it records `config_sync=...` as a statement, never a failure. - **Pairs are parallel jobs.** `max_parallel` now defaults to **5**: each HA pair (or standalone firewall) is one unit whose members go in series, passive first, up to 5 units run at the same time, and the next starts as soon as one finishes; no unit waits for another. Documented in `docs/execution.md` (which still said units ran one at a time).
- **The install waits for the commit queue.** A config sync leaves a commit in the passive member's queue, and the install is refused ("There are pending jobs in the commit task queue") until it is empty: it failed `c2` four seconds after the sync in the first run. The sync step and the install now wait for the queue to empty (up to `sync_timeout_s`, polling every `poll_interval_s`) instead of failing a firewall that is merely busy.
- **A failed firewall says where it stands.** "Failed, 0 of 6 finished" hid that two firewalls were on the new version.
